# Astrological Data Sources and Coverage Recommendations

**Reviewed:** October 25, 2026  
**Purpose:** Identify publicly accessible source data and historical references relevant to the professional gaps recorded in `docs/audit/2026-10-25-ASTROLOGY_REVIEW.md`. This is a research and implementation guide, not an endorsement of one astrological tradition or a grant of redistribution rights.

## Executive Summary

Several items called “missing data” in the audit are more accurately **coverage or product-policy gaps**. Astraya already ships Swiss Ephemeris planetary/main-asteroid data and a fixed-star catalogue, but the current natal calculation selects only seven fixed stars. It also has the Paulus seven lots and a curated body registry, but not every historical lot variant or every minor body exposed by Swiss Ephemeris.

Astronomical catalogues provide identities, observations, astrometry, or orbital elements; they do **not** provide universally accepted astrological meanings, orb rules, or traditional formula conventions. Those require named historical sources and explicit, versioned choices. Do not import an undifferentiated “astrology dataset” or treat a modern star/asteroid name as evidence of a traditional interpretation.

## Current Astraya Coverage

- `public/ephe/sefstars.txt` is already present. Swiss Ephemeris uses this file for fixed-star calculations; the upstream documentation describes a catalogue of about 800 stars. Astraya’s natal chart selects seven prominent stars in `src/domain/chart-compute.ts` rather than exposing the entire available catalogue.
- `public/ephe/sepl_18.se1`, `public/ephe/semo_18.se1`, and `public/ephe/seas_18.se1` are already present. `src/astrology/bodies.ts` registers Chiron and the four main-belt asteroids; Pholus is not currently registered. Confirm exact body/file support in the installed WASM build before promising additional objects.
- `src/astrology/arabic-parts.ts` implements Paulus’s seven Hermetic lots with sect reversal and source metadata. It intentionally excludes other authors’ Eros/Necessity variants and family lots.
- `src/astrology/horary.ts` implements a small, explicitly scoped subset of Lilly’s considerations before judgment, not a complete horary judgment system.

**Implication:** First expose and accurately label what is already supported. Download more data only for a defined feature, period, coordinate convention, and license.

## Recommendations for Astraya

### Immediate: use data already shipped

1. Add a searchable fixed-star picker backed by the current Swiss star file. Keep the seven-star natal set as a simple preset, and let advanced users select more stars without requiring Gaia integration.
2. Store the Swiss star identifier/designation, source-file version, reference epoch, and any chosen orb/interpretive authority as structured metadata. Treat star-name catalogues as naming/cultural data only.
3. Add Pholus as a candidate body only after confirming the installed `sweph-wasm` build, the available asset’s valid date range, body identity, visibility/aspect defaults, and real-engine test results. The upstream standard distribution alone does not prove the repository’s exact WASM package exposes the same behavior.

### Next: selected catalogue and technique expansions

4. For every proposed asteroid or star, define a minimal record: canonical key, external identifiers, source/version, ephemeris provider/body code, valid date range, naming aliases, default visibility, aspect participation, and export representation.
5. Download one asteroid ephemeris file per deliberately selected numbered object, not the bulk archive. Validate an epoch near both ends of its supported date range and test through the production `EphemerisProvider` path.
6. Add lots only as source-specific records: author/work/edition/locator, base and operand points, day/night reversal, zodiac frame, and verification fixture. Keep Paulus, Valens, Dorotheus, and later authors’ variants distinct even when labels coincide.
7. Build horary automation from a named source profile (beginning with Lilly only if that is the declared scope). Keep question-dependent judgment inputs visible and do not imply that one downloaded text is a complete machine-readable rule set.

### Validation and governance

8. Create small, checked-in fixtures for a chosen set of fixed stars and minor bodies. Record query parameters and source/version, then independently compare selected results with JPL Horizons after normalizing center, time scale, epoch, reference plane, and apparent/geometric convention.
9. Keep the production numerical authority as Swiss Ephemeris behind `EphemerisProvider`; use Gaia, MPC, and JPL as research/identity/independent-validation sources unless a deliberate engine decision is approved.
10. Before adding any file to `public/` or shipping it in a release, document its source URL, retrieval date, checksum, date/epoch coverage, attribution, license/redistribution basis, and update process. Re-check source terms; downloadable does not mean unrestricted redistribution.
11. Put formulas, source authorities, profile identity, and provenance in structured catalogue/UI/export metadata. Do not alter immutable interpretation-corpus prose to carry calculation policy.

## Source Maintenance

The astronomical archives and downloadable catalogues can change. Re-check upstream versions and terms whenever adding or refreshing data. Keep only sources that the project can lawfully redistribute and whose identities/epochs can be preserved. This document lists research starting points; it does not declare new data adopted into Astraya.
