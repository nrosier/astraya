# Astrology calculation register and comparison review (2026-11-26)

**Scope:** every calculation in `src/astrology/`, `src/domain/`, `src/chart/extended-settings.ts`, `src/ephemeris/` and `src/time/` that produces an astrological number, a classification or a date. Rendering code (`src/chart/` wheels, glyphs, maps) is out of scope unless it decides a value.

**Question asked:** is each calculation based on a referenced source, or is it an Astraya decision? Where other software is referenced, does it calculate the same way, and if not, why?

**Branch reviewed:** `main` at `a010c11a` plus the merged #1407 work (lunar phase return, fixed-star parans). The Rise/set screen (#1981) and the Trutine screen are UI only; their calculations (`src/domain/rise-set-chart.ts`, `src/domain/trutine.ts`) are already on `main` and are included.

## 1. Method

1. Each module's `@module` header (`@purpose`, `@conventions`) and its in-code citations were read, then checked against the constants in the code. Where the header and the code disagree, the code was taken as the behaviour and the header is reported as drift.
2. Each calculation was classified with one basis code (section 2).
3. Each was compared with the reference software named in the repository:
   - **Solar Fire Deluxe** (Esoteric Technologies): the user guide held in the repository (`esoteric-solar-fire-deluxe-user-guide-undated`, text at `docs/references/text/esoteric-solar-fire-deluxe-user-guide-undated.txt`). This is the main comparator, because Astraya's #1407 features are modelled on it. Line numbers below are lines of that text file.
   - **flatlib** and **Kerykeion**: their source on GitHub, read on 2026-11-26 (`flatlib/const.py`, `flatlib/dignities/accidental.py`, `flatlib/tools/arabicparts.py`; `kerykeion/settings/config_constants.py`).
   - **Swiss Ephemeris** (Astrodienst): the engine Astraya calls, documented in `astrodienst-swiss-ephemeris-general-documentation` and `astrodienst-swiss-ephemeris-programmers-documentation`.
   - **Astro-Seek, Astrolog 8.00, Morinus, PyAstra, Astrodienst web pages**: cited by Astraya's own code or by `docs/domain/ORBS.md`. They were **not re-checked** in this review. Their comparison column repeats what the code records.
4. No test was run and no code was changed. This is a register and a comparison, not a fix.

## 2. Basis codes

| Code | Meaning                                                                                                                                                              |
| ---- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| S    | **Source-backed.** A held text (book, manual or paper in `docs/references/sources.json`) gives the rule or the number, and the code cites it with a page or section. |
| P    | **Program-backed.** The rule follows another program's documented behaviour (Solar Fire, Astro-Seek, Astrolog), not a primary astrological text.                     |
| E    | **Engine.** Swiss Ephemeris computes it; Astraya passes inputs and reads the result.                                                                                 |
| R    | **Astraya reading.** A source names the technique but leaves a detail open, and Astraya chose how to fill it. The choice is recorded (issue or owner decision).      |
| A    | **Astraya decision.** No source gives the value or rule. It is Astraya's own convention, an owner decision, or a computing choice (search steps, caps, tolerances).  |
| A?   | **Undocumented decision.** As A, but the code does not say it is a convention and cites nothing. These are the ones to look at first.                                |

Search steps, bisection tolerances and sample caps (for example `SAMPLE_STEP_DAYS`, `MAX_ELECTION_SAMPLES`) are computing choices, not astrology, and are listed only where they can change a result.

## 4. Findings

Ranked most important first. None of them is a JPL-gate accuracy problem: every planetary position comes from the engine.

### F-01 — Tertiary and minor progressions use the synodic month; Solar Fire uses the 27.32-day lunar cycle (C-55, C-56)

Tracked in #2032. **Resolved by #2032:** the code now uses `TROPICAL_MONTH_DAYS` = 27.32158648 days, the owner's decision (2026-11-27). The owner's note gave the Moon's rate as 13.176358°/day = 360° / 27.32158648 d; that is an arithmetic slip, because 13.176358 is the rate for the sidereal month (27.32166 d). The tropical rate is 360 / 27.32158648 = 13.176394°/day, and the code and its docs use the tropical figure.

- **What differs:** Astraya's tertiary is one day per synodic month (29.530588 days). Solar Fire's mean tertiary is one day per 27.32158648-day lunar cycle, and it also offers a true tertiary. Minor progressions differ the same way. Solar Fire's own example of a 29.53-day rate is called a "Lunar Progression Rate", a separate user rate.
- **Size:** the rates differ by about 8%. By age 40, Astraya's tertiary chart is cast about 40 days of ephemeris earlier than Solar Fire's (40 × 365.2422 / 29.530588 ≈ 495 days, against 40 × 365.2422 / 27.32158648 ≈ 535 days). The progressed Moon then sits in a different sign.
- **Why:** the module gives no source for the synodic month. Its header also says "neither technique has competing schools for angle movement". That is about the angles, but the month length is itself contested: Solar Fire uses the 27.32-day cycle, and some authors use the synodic month (general knowledge; no held source on tertiary progressions).
- **Done (#2032):** the owner chose Solar Fire's 27.32158648-day month (decision on #2032). It is cited to the Solar Fire guide, and the basis is now S / P. Solar Fire's true tertiary (actual lunar months) is still not implemented, and that remains a difference to document in the differences doc (#2036).

### F-02 — Year lengths: two tropical constants, and zodiacal releasing does not use Valens's 360-day year (C-61, C-64, C-65)

Tracked in #2033.

- `progressions.ts` uses 365.2422 days (Meeus, #1403). `firdaria.ts` still has its own `TROPICAL_YEAR_DAYS = 365.2425`, the Gregorian mean that #1403 replaced.
- The `primary-directions.ts` header says Naibod is 360 / 365.2425, but the code reuses `NAIBOD_DAILY_MOTION`, which is now 360 / 365.2422.
- **Size:** about 0.0003 days a year, so about half an hour over a 75-year firdaria cycle. A period start can move by minutes, and a date shown to the day can change only when it falls near midnight.
- **Why:** #1403 changed one constant and not its copy.
- Zodiacal releasing uses 365.2425-day years and months of a twelfth of that. Brennan (2017, ch. 18, p. 558) says Valens used a 360-day year and 30-day months, so each Astraya period runs about 1.5% long: about 157 days over a 30-year Level 1 period.
- **Resolved (#2033):** firdaria reuses `TROPICAL_YEAR_DAYS` from `progressions.ts`; the timing timeline, angle transits and the cycles screen import it too, and the `primary-directions.ts` header now reads 360 / 365.2422 = 0.9856473°. Zodiacal releasing uses Valens's 360-day year and 30-day months (`RELEASING_YEAR_DAYS`, `RELEASING_MONTH_DAYS`). The changed assertions are listed on #2033.

### F-05 — Defaults that differ from Solar Fire by choice (C-31, C-53, C-61, C-22)

## 5. What holds

- **Every planetary, house, ayanamsa, eclipse and rise/set number comes from Swiss Ephemeris** through the provider boundary, with the JPL 0.2″ gate. None of the differences above is an ephemeris difference.
- **Traditional techniques are source-backed with page locators:** dignities, triplicities, faces, almuten (Lilly), lots (Paulus/Greenbaum), firdaria (Bonatti), zodiacal releasing (Valens), primary directions (Makransky), the Trutine (Lilly), horary considerations (Lilly), composite and Davison (Solar Fire and Davison).
- **Where Solar Fire was the model, Astraya matches it:** cazimi, combust and under-the-beams orbs; the Part of Fortune options; the void-of-course definition; the Via Combusta; the horary Ascendant limits; the Naibod and secondary rates; solar arc kinds and multipliers; solar arc in declination; rise/set horizons; the paran orb range; composite houses; and the transit orb windows.
- **Astraya's own conventions are mostly labelled as such**, with an issue number: the default orbs (#1602), the fixed-star orb (#869), the transit presets (#416), rectification weighting (#1445), the hyleg rules (#1799), and the harmonic-age reading (#1407). The exceptions found by this review (F-04) are now cited or recorded (#2035).
- Where Astraya and flatlib differ (combust 8°30′ against flatlib's 8°, under the beams 17° against 16°, combustion only in the same sign), Astraya follows Lilly, and flatlib cites no source.
